ARRANQUE

Abrir Docker Desktop. Desde la carpeta del repositorio:

  npm run staging:setup
  npm run staging:dev

Para aplicar cambios de politica al staging existente con comprobacion de
historicos y respaldo cifrado previo:
  npm run staging:policy-setup

El respaldo AES-256-GCM se guarda fuera de Git en el runtime/backups. Su clave
esta protegida con DPAPI del usuario Windows; se verifica el descifrado, no
se ensaya automaticamente la restauracion de cada respaldo de policy-setup.
El ensayo logico de un respaldo actualizado distinto paso; ver la seccion siguiente.

El segundo comando mantiene el frontend en la terminal. Tambien existe
staging:launch para ejecutarlo en segundo plano, con logs en el directorio
temporal del proyecto; no reemplaza servidores ajenos en el puerto 3017.

staging:setup usa una configuracion separada, copia las migraciones y levanta
su propio stack Docker. No usa supabase link, db reset ni comandos remotos.
La semilla es transaccional y se instala una sola vez. Los siguientes arranques
conservan las asistencias, los recibos y los datos locales ya creados.

Los archivos de ejecucion se guardan en:
  %TEMP%\opencode\pottery-gym-local-staging

El frontend no carga .env/.env.local ni la configuracion Vite de produccion.
Recibe unicamente URL local y clave anon publica. La clave administrativa se
usa solo en memoria para crear usuarios sinteticos durante el bootstrap.

PRUEBAS

Con el frontend funcionando:

  npm run staging:test

Ejecuta exclusivamente 45 escenarios con Auth, REST/PostgreSQL, Edge y navegador
reales del staging local, con un worker y cero retries. Bloquea backends remotos y no utiliza
la clave service_role para las operaciones de negocio. Los fixtures de cada
ejecucion tienen UUIDs nuevos y se conservan; no hay borrado masivo de QA.
Los datos de demostracion se comparan antes y despues para comprobar que no
fueron alterados.

Casos verificados:
- Reserva/provisional sin consumo; presencia, falta y cancelacion tardia cobran
  una clase al finalizar. Cancelacion con al menos ocho horas no consume.
- Pago pendiente/null o vencimiento necesitan aprobacion individual por empleado.
- Sin credito puede aprobarse cortesia; la penalizacion sin credito es incidencia.
- Solo el propietario exime/revierte una penalizacion. Cambiar falta a presencia
  no borra el cargo; superadministrador no puede autoasignarse como propietario.
- Respuesta perdida despues del commit: reintento exacto sin otro descuento.
- Recargar/remontar recupera el intento original para asistencia, excepcion,
  cancelacion y exencion; no crea otro UUID ni reescribe los argumentos.
- Alumnos homonimos: destinatario explicito por ID, sin crear otra persona.
- Otro taller y lector limitado: RLS, RPCs, permisos y API Edge reales.
- Creditos manuales: evidencia y aprobacion del propietario, ledger separado
  del scalar legado, conciliacion completa solo si el saldo es conocido.
- Liquidacion del perfil solo contra fuente original; no se sustituye por un
  periodo siguiente, otra Gift Card o un nuevo credito manual.
- Aprobacion/liquidacion/exencion: respuesta perdida tras commit, o recibo/rechazo
  SQL seguido de fallo de recarga, conservan el intento tras reload completo.
- Recuperar datos es solo lectura; el replay explicito envia la misma key/revision.

Verificacion final 2026-10-12: 45/45 reales, 370/370 regresiones, 37/37 unitarias,
TypeScript/build y lint aprobados; pgTAP 3/3. La suite real completa duro 13 min.
El rollout manual, respaldo y limites se registran en docs/manual-credit-phase.txt.

Seguimiento de providers: 524/524 regresiones locales y 40/40 unitarias pasaron,
con TypeScript/build. Estas pruebas usan transporte simulado, no certifican de
nuevo los 45 escenarios reales anteriores. Ver docs/provider-integrity-fixes.txt.
No se renovaron los grants vencidos ni se aplico el schema mixto por este seguimiento.

ENSAYO DE RESTAURACION

  npm run staging:restore-rehearsal

Toma un snapshot solo lectura del staging aprobado, guarda dump/roles/configuracion
en un archivo AES-GCM con clave DPAPI y lo relee del disco. Restaura en un cluster
Docker nuevo en RAM, con Auth/PostgREST propios, sin modificar la base original.
Compara todas las filas y permisos, genera estadisticas con ANALYZE y prueba login,
lecturas REST acotadas, denegaciones, replay y navegador desktop/mobile.
Solo elimina los contenedores/red que creo y conserva el respaldo y reporte.

Resultado 2026-10-12: PASSED, 83 tablas/13503 filas, 31 roles y 24 migraciones.
Los grants del lector estaban vencidos: su denegacion se verifico sin renovarlos.
Detalle y limites: docs/restore-rehearsal.txt. No certifica PITR, archivos externos,
recuperacion off-host o restauracion de todos los respaldos antiguos.

PARADA

  npm run staging:stop

Solo detiene este frontend/stack y conserva su snapshot local. No elimina
volumenes ni detiene el stack anterior en 54321. No publiques los puertos
de Docker o Studio en Internet: es un entorno de desarrollo local.

LIMITES

No conecta una preview publica de Vercel a este equipo. No demuestra todavia
un despliegue remoto o recuperacion off-host/PITR. El ensayo logico local paso.
El contrato MCP sigue
sin servidor/transporte activo. Los grants del lector caducan deliberadamente;
un reinicio no renueva permisos de forma silenciosa.

El CLI publica los puertos Docker en 0.0.0.0/::, no solo en loopback. Segun el
firewall del equipo, API, DB y Studio pueden ser accesibles desde la LAN. Usar
solo datos sinteticos y restringir el acceso con el firewall antes de compartir
la red. Esta herramienta no modifica automaticamente el firewall del sistema.

Tras un dia, la prueba de lectura acotada puede fallar por expiracion de grants;
se necesita una nueva autorizacion sintetica explicita, no un reset de datos.
El runner Windows usa el ejecutable nativo, no el shim Node. Un timeout de red
no acredita rollback; comprobar el recibo antes de crear una operacion diferente.
Los caches Vite de staging y regresion estan separados.

Los temporales con saldo manual positivo sin periodo/bono atribuible requieren
conciliacion explicita completa con evidencia, no cortesia que suponga saldo cero.
Si el saldo es desconocido, no se concilia; un derecho nuevo requiere evidencia
independiente del propietario. Ambiguedades Gift quedan vetadas de forma durable.
Los ajustes genericos de membresia permanecen bloqueados. Las incidencias
pendientes solo se liquidan por el propietario desde la ficha contra la fuente
original valida; no hay liquidacion automatica ni cargo al siguiente periodo.

Antes de produccion faltan revision visual, recuperacion especifica del entorno
productivo, reglas de negocio pendientes y autorizacion del rollout coordinado.
